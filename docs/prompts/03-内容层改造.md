# Prompt #03 · 内容层改造：教材拿不到，改用联网检索

- 日期：D2
- 触发：我把教材 PDF 这条线否掉了
- 关联 commit：`feat(content): 内容层改为联网检索+缓存（AI #03）`

## 我的原始表述

> 教材 pdf 我没找到在哪里下载。然后到了真正的场景肯定不是每个教材都要下载，
> 是通过联网搜索出来的。

## 这条反馈为什么重要

我原来的设计里，`chunks` 表假设"教材 PDF 已在手上"。这个假设在两个地方崩：

1. **覆盖面**：大学物理教材版本极多（马文蔚、程守洙、张三慧…），不可能全覆盖；
2. **法律与工程成本**：教材是版权作品，公开仓库不能放，复现者也没有。

## 改造方案：把"书"拆成三层

| 层 | 来源 | 是否依赖教材 |
|---|---|---|
| 骨架层 `chapters` / `kps` | 通用章节表 + 真题反推 | **否** |
| 内容层 `contents` | 联网检索 → 抽取 → 落盘缓存 | 否（按需抓） |
| 原文层 `chunks` | 有教材时补充，没有就留空 | 可选 |

关键点：**骨架不依赖教材，内容按需抓取**。这样即使一个学生用的小众教材，
只要章节骨架对得上，系统照样能用。

## 新增两张表

- `sources`：url / domain / title / kind / **trust** / fetched_at
  为什么要有 trust：网上内容质量参差不齐，必须能回答"这句话你从哪抄的、可信吗"。
- `contents`：kp_id → 抽取后的"3 句话讲解 + 1 个例子"，`UNIQUE(kp_id, source_id)` 防重复抓取。

## 引入的新风险（诚实记录）

1. **质量不可控**：百科内容可能过时或用词与教学不符 → 需要 trust 排序 + 至少 2 个来源交叉。
2. **延迟**：冷启动每个知识点要一次搜索 → 必须缓存，并统计命中率。
3. **搜索 API 成本**：需要一个搜索后端（Bing/Serper/Tavily 或自建 SearXNG），免费额度要算清楚。
4. **引用合规**：输出必须带来源链接，不能把抓来的整段当自己的话。

## 对比赛材料的影响

技术文档里，这一节正好回答"意图控制与架构约束"：
为什么把"书"拆成三层、为什么内容要带 trust、为什么缓存是硬要求。
